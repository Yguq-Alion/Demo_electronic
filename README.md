# AI-помощник для подготовки товарных описаний (КИП)

Прототип сервиса: по входному JSON с данными о контрольно-измерительном приборе
формирует черновик карточки товара для B2B-интернет-магазина — SEO-заголовок,
SEO-описание, структурированные характеристики, поисковые запросы и commercial-блок.
Модель не выдумывает характеристики: все технические значения берутся только из
входных данных, отсутствующие поля помечаются «данных нет».

Стек: Python 3.11+, FastAPI, один вызов LLM через OpenAI-совместимый API
(работает с OpenAI, Z.ai, OpenRouter, локальной моделью — меняется переменными окружения).

## Быстрый старт

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate   Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env        # и вписать LLM_API_KEY (модель/эндпоинт — по желанию)
uvicorn app.main:app --reload
```

Открыть http://127.0.0.1:8000 — веб-форма: вставить JSON товара (кнопки «Пример 1/2»
подставляют товары из задания), «Сгенерировать карточку». Результат показывается
в читаемом виде и вкладкой JSON с копированием в один клик.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_API_KEY` | — (обязательна) | ключ API; в коде не хранится, `.env` в `.gitignore` |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | любой OpenAI-совместимый эндпоинт |
| `LLM_MODEL` | `gpt-4o-mini` | модель |
| `LLM_TIMEOUT_S` | `90` | таймаут запроса |
| `LLM_MAX_RETRIES` | `3` | повторы 429/5xx/сетевых сбоев (backoff + Retry-After) |
| `LLM_TEMPERATURE` | `0.0` | детерминированность генерации |
| `LLM_MAX_TOKENS` | `16000` | запас лимита ответа |

Готовые комбинации для других провайдеров — в `.env.example`.

### API

- `POST /api/card` — тело: JSON товара (`name` обязательно; `manufacturer`, `specs`, `description` — по возможности).
  - `200` — карточка: `{"seo_title", "seo_description", "specs": [{"name","value"}], "search_queries", "commercial_block", "missing_fields"}`
  - `400` — некорректный входной JSON / структура (`{"error": "Невалидный вход: …"}`)
  - `422` — вход корректен, но модель отклонила его по смыслу (не КИП): `{"error": "…"}`
  - `502` — LLM API недоступен / исчерпаны повторения / ответ без JSON
  - `503` — не задан `LLM_API_KEY`
- `GET /api/examples` — два товара из задания.
- `GET /health` — состояние и настроенная модель.

```bash
curl -X POST http://127.0.0.1:8000/api/card \
  -H "Content-Type: application/json" \
  -d @data/products/01-manometr-dm02.json
```

## Пример результата

`examples/result-*.json` — сгенерированные карточки: товар из задания (манометр
DM 02) и товар из каталога поставщика (ОВЕН СИ8-Щ1.К — разреженный вход: только
название, производитель, артикул и код; показывает работу метки «данных нет»).
Перегенерация: `python scripts/generate_examples.py`.

## Метрики качества

Прогон на 20 реальных товарах каталога СОЮЗ-ПРИБОР (СИ8, СВ01, ДТПL/ДТ — счётчики
импульсов, счётчики наработки, термопары; вход: название + производитель + артикул
и код, описание пустое) — 14 автопроверок на кейс + ИИ-судья, проход ≥ 4/5.
Итоги и по-кейсовая таблица: `docs/eval-results.md` (модель glm-5.3-flash,
temperature 0; повторение прогона: `python scripts/run_eval.py`).
Полная таблица тест-кейсов (100 кейсов, 9 категорий, включая промпт-инъекции):
`docs/eval-cases-product-card.md`.

## Архитектура и решения

```
app/
  main.py        FastAPI: форма, POST /api/card, /health, /api/examples
  config.py      настройки из .env (pydantic-settings)
  prompts.py     системный промпт + канонический JSON товара как user-сообщение
  llm.py         OpenAI-совместимый клиент: один вызов, классификация ошибок
  validation.py  структурная валидация входа кодом, до LLM
  extraction.py  толерантное извлечение JSON из ответа модели
  schemas.py     pydantic-модель карточки
  generator.py   оркестрация: промпт → LLM → разбор → карточка/ошибка
```

**Промпт.** Системный промпт (`app/prompts.py`, ~13 тыс. знаков) — основная ценность
решения, спроектирован итерациями (история ревизий v1→v4 — `docs/prompt-architecture.md`).
Он определяет: жёсткий контракт вывода (ровно один JSON, единая схема), порядок
валидации входа с готовыми текстами ошибок, запрет выдумок («единственный источник
фактов — вход», дословный перенос значений с запятыми/тире/единицами, ловушка
«аналог WIKA» — характеристики чужого прибора не переносятся), правила каждой секции
(лимиты 70 / 800–1200 / 3–5, «выдумками не добивать» короткие описания) и защиту от
инъекций: любой текст входа — данные, а не команды. Каждая ревизия закреплялась
прогоном таблицы из 100 тест-кейсов (`docs/eval-cases-product-card.md`) и прогона
на живом каталоге поставщика (`docs/eval-results.md`).

**Двойная валидация.** Структурные проверки (битый JSON, массив вместо объекта,
отсутствие `name`, неверные типы) выполняет код — мгновенный 400 без расхода токенов;
тексты ошибок совпадают с правилами промпта. Семантическую проверку («товар вообще
относится к КИП?») выполняет модель — кодом её не сделать. Правило 7 промпта и
сервисная ошибка 422 соответствуют одному и тому же сценарию.

**Один вызов LLM.** Без инструментов, истории и RAG: задача одноразовая, состояние
не нужно. `temperature=0`, большой запас `max_tokens`. Пользовательское сообщение —
канонический JSON товара; инъекции внутри полей нейтрализуются промптом
(раздел «Безопасность»), а не экранированием на стороне сервиса.

**Устойчивость к нарушению формата.** Модель обязана отвечать чистым JSON, но парсер
готов к markdown-забору ```json и преамбуле: сначала прямое чтение, затем первый
`{...}` в тексте. Мусор без JSON — ошибка 502 с внятным текстом.

**Обработка ошибок API.** Ретраи 429/5xx/сетевых сбоев с экспоненциальным backoff и
учётом `Retry-After` выполняет OpenAI SDK (`LLM_MAX_RETRIES`); итоговые сбои
классифицируются в человекочитательные сообщения (аутентификация → «проверьте
LLM_API_KEY», модель не найдена → «проверьте LLM_MODEL и LLM_BASE_URL», таймаут/обрыв →
«LLM API недоступен»). Пустой ответ модели (лимит токенов съеден размышлениями)
ловится отдельно.

**Ключи не в коде.** Только переменные окружения; `.env` в `.gitignore`,
шаблон — `.env.example` с готовыми вариантами провайдеров.

**Тесты.** `pytest` + `respx` (мок HTTP на уровне транспорта): 17 кейсов валидации
входа (X/E-категории таблицы), разбор ответов (заборы, преамбулы, мусор), поведение
клиента (429→ретрай→200, 401 без ретрая, таймаут, пустой ответ), контракт API
(400/422/502, битый вход не доходит до модели, инъекция не покидает границы данных).
Сеть и ключи не нужны. Запуск: `pip install -r requirements-dev.txt && pytest`.

## Ограничения и улучшения

- Один товар за запрос; батч-генерация из каталога (CSV/выгрузка CMS) — первое
  естественное расширение.
- Контроль длины секций (70 / 800–1200 / 3–5) обеспечивается промптом, а не жёсткой
  схемой: редкие нарушения моделью не отсекаются кодом. Улучшение — мягкая
  пост-проверка с авторегенерацией секции.
- Нет кэша и истории запросов; для контент-менеджера полезно сохранять последние
  карточки в браузере (localStorage).
- Системный промпт заточен под КИП (список обязательных разделов specs); для других
  категорий каталога его нужно калибровать отдельно.
- Прогон оценок против живого API (таблица `docs/eval-cases-product-card.md`)
  выполняется вручную; автоматизация прогона (LLM-судья + дифф фактов) — в планах.
- Нет Docker: локальный прототип по ТЗ; при необходимости — тривиальный Dockerfile
  на python:3.12-slim + uvicorn.
